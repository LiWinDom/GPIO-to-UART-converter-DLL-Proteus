# Руководство для разработчика: модификация функционала библиотеки GPIO↔UART

Сборка и деплой
1. Откройте проект `gpio2uartdll.vcxproj` в MS Visual Studio.
2. Соберите конфигурацию `Release` (или `Debug`).
3. Возьмите `gpio2uartdll.dll` из папки `Release` и подключите как пользовательскую модель в Proteus.
4. Логи модели выводятся через `m_instance->log(...)` и помогают отладке.

Краткая структура кода
- `GPIO_UART_Converter` — основной класс модели.
- `setup()` в [GPIO_UART_Converter.cpp](GPIO_UART_Converter.cpp) — привязка пинов и начальная настройка.
- `simulate()` — основная синхронная логика: обработка `CS`, `RE`, `WE`, управление шинами DO/DI.
- `callback()` — обработка асинхронных событий UART (TX event=1, RX event=2).
- `processConfig()` / `readConfig()` — точка входа для конфигурационных регистров.
- `handleUART_TX()` / `handleUART_RX()` — конечные автоматы передачи/приёма UART.

Условные обозначения сигналов
- `CS` — active-low chip select. Если `CS`=1, DO должна быть в высокоимпедансном состоянии (FLT).
- `WE` — active-low write enable, модель реагирует на фронт 0→1 (`isposedge()`).
- `RE` — active-low read enable; при `RE`=0 MCU читает DO.
- `C/D` (`m_CD`) — выбор конфигурации (1) или данных (0).
- `UART_TXD` / `UART_RXD` — UART линии (idle = logical 1).
- `INT` — аппаратный прерывающий вывод (active-low).

Регистры и адреса
- Адреса регистров в интерфейсе конфигурации: 0x00..0x05 используются по умолчанию.
  - 0x00 — control register (bit0 = UART enable, bit1 = RX int, bit2 = TX int)
  - 0x01 — baud code
  - 0x02 — parity mode (0=None,1=Odd,2=Even)
  - 0x03 — stop bits (0=1 stop, 1=2 stop)
  - 0x04 — overwrite/ discard on RX overrun
  - 0x05 — clear-on-read flag for RX
- Статус регистр на адресе 0x0F (при чтении через параллельный интерфейс) возвращает флаги: RX ready, TX busy, RX busy, TX complete.

Где править — быстрые рецепты

1) Добавление нового конфигурационного бита / регистра
- Файлы: [GPIO_UART_Converter.h](GPIO_UART_Converter.h) и [GPIO_UART_Converter.cpp](GPIO_UART_Converter.cpp).
- Шаги:
  1. В `GPIO_UART_Converter.h` добавьте поле (например `BOOL m_newFeature;`).
  2. В `processConfig()` добавьте соответствующий `case` или добавьте бит в `case 0x00`.
  3. В `readConfig()` верните значение нового поля для чтения.
  4. Добавьте поясняющий `m_instance->log(...)` для отладки.
- Тест: через Proteus установите `CS=0`, `WE` подайте rising edge с нужным байтом на `DI`, затем прочитайте через `RE`.

2) Добавление новой скорости UART
- Где это задаётся: `processConfig()` в [GPIO_UART_Converter.cpp](GPIO_UART_Converter.cpp) в `case 0x01`, а для чтения текущего кода используется `readConfig()` в том же файле.
- Что менять:
  1. Выберите свободный код скорости в поле `m_baudCode`.
  2. Добавьте новый `case` в `switch(m_baudCode)` и укажите реальное значение `baud`.
  3. Если кодировка скорости меняется, проверьте, что `readConfig()` по адресу `0x01` возвращает тот же код.
  4. При необходимости обновите внешний код или документацию, которая пишет значение в регистр `0x01`.
- Что важно не забыть:
  - После выбора `baud` обязательно пересчитать `m_bitTime = 1000000000000ULL / baud`.
  - Проверьте, что таймеры в `handleUART_TX()` и `handleUART_RX()` по-прежнему используют `m_bitTime` без дополнительных поправок.
  - Если добавляете очень высокую скорость, протестируйте передачу и приём отдельно, потому что ошибки чаще всего появляются именно в `callback()` и на границах бита.

3) Добавление нового UART-режима
- В этом проекте под UART-режимом понимается формат кадра: parity и количество stop-битов. Сейчас это разделено на два регистра: `0x02` для parity и `0x03` для stop bits.
- Где это задаётся: `processConfig()` в [GPIO_UART_Converter.cpp](GPIO_UART_Converter.cpp) и соответствующие поля в [GPIO_UART_Converter.h](GPIO_UART_Converter.h) — `m_parityMode` и `m_doubleStop`.
- Что менять, если нужен новый режим:
  1. Определите, что именно добавляется: новый вариант parity, другой формат stop bits или полностью новый формат кадра.
  2. Расширьте кодировку в `processConfig()` для адресов `0x02` и/или `0x03`.
  3. Обновите `readConfig()`, чтобы чтение возвращало новый код или флаг без потери обратной совместимости.
  4. Проверьте TX и RX FSM: в `handleUART_TX()` нужно корректно формировать кадр, а в `handleUART_RX()` — правильно проверять parity и stop bits.
- Если режим меняет формат кадра глубже, чем parity/stop bits:
  - Добавьте или расширьте поле состояния в `GPIO_UART_Converter.h`.
  - Убедитесь, что `resetDevice()` инициализирует новый режим в безопасное значение по умолчанию.
  - Добавьте логирование через `m_instance->log(...)`, чтобы было видно, какой режим был выбран.
- Что проверить после изменения:
  - Совместимость со старыми кодами `0x02` и `0x03`.
  - Корректную генерацию стоп-битов при передаче.
  - Корректную обработку parity/формата при приёме, особенно если режим должен выставлять ошибку или игнорировать байт.

4) Добавление нового пина
- В `GPIO_UART_Converter.h` добавьте `IDSIMPIN2* m_NEWPIN;`.
- В `setup()` получите пин через `instance->getdsimpin("NAME", TRUE)` и установите `settiming`/`setstates`/`setstate`.
- Используйте `m_NEWPIN->setstate(time, details::DELAY, SHI/SLO)` в `simulate()` или `callback()` при необходимости.

Логирование и отладка
- Используйте `m_instance->log("text")` для быстрых сообщений.
- Рекомендуемые сообщения: вход в `startUART_TX`, завершение `TX`, ошибка паритета, ошибка фрейминга, переполнение RX.

Пример патча — добавить бит "clear on read" (уже реализовано в модели как `m_clearOnRead`):
1. Хедер: добавлен `BOOL m_clearOnRead;` (см. [GPIO_UART_Converter.h](GPIO_UART_Converter.h)).
2. `processConfig()` в `case 0x05` записывает флаг: `m_clearOnRead = data & 0x01;`.
3. В `simulate()` при `RE` rising edge и `CD==0` очищаем `m_rxData` если `m_clearOnRead`.

Тестирование
- Ручное: собрать DLL → загрузить в Proteus → генерация сигналов на `UART_RXD` / `DI` → анализ логов и состояния `DO` / `INT`.
- Автоматизация: можно написать тест-харнесс, имитирующий вызовы методов `simulate()` и `callback()` (требует изучения SDK для корректной инициализации `IINSTANCE`/`IDSIMCKT`).

Рекомендации по внесению изменений
- Сохраняйте поведение внешнего интерфейса пинов и регистров, если не планируете менять API.
- Добавляйте подробные логи при новой функциональности.
- Проводите обратную совместимость: добавляйте новые биты/регистры, а не изменяйте существующие значения кодов.
